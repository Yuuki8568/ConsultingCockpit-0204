## 試験の境界

- `bun run test:security`：実Web Crypto＋fake-indexeddbによる隔離試験。通信のみスタブ。14件合格（40 assertions）。旧暗号互換、HMAC分離、破損保持、遅延施錠、保存失敗、CAS、別タブ、録画欠落、独立控え、CSV、鍵変更ジャーナル復旧等。
- `bun run test:blackbox`：実HTTPサーバー・実SQLite・実認証ミドルウェア。専用ダミーアカウントを事前作成。未認証/偽token/非所有者、Origin、ヘッダー、同期競合、再鍵交換、試行制限、ログアウトを検査。実Runable OAuthは呼びません。
- `bun run typecheck:security`：実際のapp/node設定を明示して型検査。既存ルートtsconfigだけへの `tsc --noEmit` は参照先を検査しないため、このコマンドを追加。
- `bun run build:web`：成功。既存の大きなJSバンドル警告が残ります。
- サーバー用HTTPテスト・ブラウザ試験結果の最終件数は `docs/security-test-results.md` に記録。

## 追加した運用上の制約

1. 解錠済みの同一オリジンタブは1つ。Web Locks非対応ブラウザは安全側に停止。
2. データに破損がある場合、部分状態を正常と扱わず停止。保存領域を消して対処しない。
3. 旧世代の別端末はサーバーへの書き込みを拒否。旧端末に未同期編集がある場合、暗号化IndexedDB原本を保全してから復旧を設計する必要があります。
4. Mobileには世代送信を追加。生体認証のみで復帰し、検証済み世代がない場合は同期を拒否し、パスフレーズでの解錠を要求します。Mobile/デスクトップ実機試験は未実施。
5. 鍵変更の旧監査詳細・競合コピーは旧鍵で封じられたまま保持する場合があります。新規監査には現行鍵を使用します。旧パスフレーズは復旧確認前に破棄しない。
6. 録画は新形式でメモリに暗号化チャンクを集めて一括確定。大容量録画のメモリ負荷試験は残ります。
7. CORSの拒否だけで認可とみなさず、全保護RPCで本人認証を継続。リバースプロキシの信頼IP設定・MFA・DB権限は配置先で確認が必要。

## 復旧・ロールバック

コードとデータの復旧は別です。バックアップブランチを残しているためコードは戻せますが、旧コードが新形式の録画manifestを解釈できるとは限りません。

- 本番適用前：全タブを閉じ、暗号化控え（形式2なら出力時パスフレーズで実際に別環境復号）、録画の別保全、IndexedDB暗号化原本、サーバーDBスナップショットを取得。機密バックアップをGitに入れない。
- 形式2の控え：`bun security-ops/recover-backup.ts INPUT.json OUTPUT.json`。端末上でパスフレーズを非表示入力。出力は平文・0600・既存ファイルは上書きしない。録画本体は含まれません。旧形式1には元の金庫鍵/KDF情報が必要。
- 鍵変更中の切断：`rekeyJournal` と一時メディアを消さない。旧鍵で再解錠すると保存済みの冪等リクエストを再送し、新パスフレーズでの解錠を案内。新鍵で開ける場合は残りのローカル確定を再開。サーバーが競合で拒否した場合は原本を残して停止し、専門的な復旧が必要です。
- 未適用PR：PRを閉じれば本番コードはそのまま。
- 本番コードを基準版へ戻す：基準SHAから復旧用ブランチを作成し、通常のレビュー/デプロイ経路で適用。mainのforce pushは不要です。
- 新形式を書き込んだ後の復旧：新コードを止めるだけで暗号データを旧版へ変換しません。新形式対応readerを維持するか、適用前DB/端末原本へ戻す計画が必要。DB復元は後発編集を失う可能性があるため別承認。
