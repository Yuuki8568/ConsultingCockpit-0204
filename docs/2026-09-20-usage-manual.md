## 1. このアプリは何をするものか

ソロでAI業務改善コンサルを回すための管理ツール。営業前のリード管理から、受注後の案件管理、事務所全体の記録までを1つの金庫（暗号化されたデータ領域）にまとめて持つ。

外部のAIやクラウドには一切接続しない。データはこの端末と預け先（同期サーバー）の間で暗号文のまま移動し、平文で読めるのはパスフレーズを入れて金庫を開いた画面だけ。

### 3つのモード

画面上部の切り替えで3つのモードを行き来する。

| モード | 役割 | 使うタイミング |
| --- | --- | --- |
| リード | 受注前の見込み客を管理する | 問い合わせが来たとき、営業中 |
| 案件 | 受注後の仕事を9つの帳票で管理する | 受注が決まってから終了まで |
| 自社 | 事務所全体の時間・容量・承認・事故を横断で見る | 月初めの計画、月末の締め |

基本の流れは「リード → 案件 → 自社で振り返り」。リードが受注に至ったら案件を作り、案件の記録が自社の横断一覧に自動で集まる。

## 2. 起動と入口

### 2.1 開き方

1. アプリのURLを開く
2. Googleサインイン（または登録済みメール）で認証
3. 金庫のパスフレーズを入力して「開く」

サインインは「誰が開くか」の確認で、金庫の中身とは別の鍵。金庫のパスフレーズが本文を開ける唯一の鍵になる。

### 2.2 初回だけやること

初めて使う端末では金庫を新しく作る。

1. パスフレーズを決める（10文字以上）
2. 「紛失した場合、案件データを復元できないことを理解しました」に合意
3. 「金庫を作る」

パスフレーズは通信も保存もされない。紛失すると中身は誰にも復元できない。必ず紙などの安全な場所に控えを残す。

### 2.3 閉じ方・自動で閉じる仕組み

| 動作 | 内容 |
| --- | --- |
| 手動で閉じる | 上部の錠ボタン |
| 自動で閉じる | 操作が30分ないと自動で施錠（25分で予告が出る） |
| 間違い対策 | パスフレーズを5回続けて間違えると5分間停止 |

外出先や画面共有のときは「伏せる」ボタンで企業名・金額だけを隠せる。戻すときは上部の「伏せ中」を押す。伏せた項目そのものは押せないようになっている（うっかり表示に戻るのを防ぐため）。

## 3. データの守られ方（金庫の仕組み）

理解しておくと運用で迷わない、金庫の基本構造。

### 3.1 暗号化

- 方式はAES-256-GCM。パスフレーズから端末上で鍵を作り、その鍵でレコードを封する
- サーバーに送られるのは暗号文だけ。サーバー側は中身を読めない
- 施錠するとメモリ上の鍵と平文は捨てられる

### 3.2 レコードの分かれ方

データは次の単位で別々のレコードに分かれて保存される。

| レコード | 中身 |
| --- | --- |
| case:（案件ID） | 案件1件の全部。9タブの内容 |
| lead:（リードID） | リード1件の全部 |
| profile:main | 受託者プロフィール |
| template:（書類種別） | 書類雛形1件 |
| meta:app | リード通番・目標・紹介・UI状態・知見台帳・自社の月次記録 |

1案件を直してもそのレコードだけが送り直されるので、同期が重くならない。知見台帳と自社の月次記録は meta:app に入る（案件個別ではなく全案件共通の領域）。

### 3.3 同期と控え

- 変更は1〜2秒後に自動で同期キューに乗り、預け先へ送られる
- オフラインでも編集でき、つながったときにまとめて送られる
- 同じ場所を別々に直すと後から保存した側が勝ち、負けた側は設定画面に記録が残る
- 1レコードの上限は1MB（超えたレコードは同期されず、状態表示に「同期上限超過」と出る）

控え（バックアップ）は 設定 → 取込・書き出し → 「控えを取る」からJSONで書き出せる。デスクトップ版では「手元への控え」で保存先フォルダを決めて日付ごとに積み上げられる。復元は同じ画面の取り込みから行う。控えは定期的に取ること。金庫の中身を復旧できる手段はこれだけ。

## 4. リードモード

受注前の見込み客を管理する。4つのタブ。

### 4.1 ① 追加・文面

問い合わせが来たらここから登録する。

1. 企業名と担当者名（両方必須）を入れて追加
2. 紹介元や経路が分かれば記録
3. 初回メールなどの文面の叩き台をここで作れる

### 4.2 ② 一覧

登録済みリードの一覧。状態（新規・連絡中・見込み など）で並べ替えて、次に動く相手を決める。

### 4.3 ③ ダッシュボード

営業の数字を見る場所。

- 受注済みと期待の分離: 契約に至った金額と、まだ期待でしかない金額を分けて表示する。期待を売上に足し込まないための区分
- 営業工数の記録: 月ごとに営業に使った時間を記録する。「+ 今月分を追加」で当月の行ができる

### 4.4 ④ 営業プロセス

個別リードの詳細。商談前の準備と適格性の確認を行う。

| 区画 | 内容 |
| --- | --- |
| 案件の見立て | 0=未確認、1=ある程度、2=確認できている の3段で採点 |
| 受注前の7項目 | 受けていい仕事かの確認。空欄は未確認のまま残る。「問題ない」とは読み替えない設計 |
| FDE適合確認 | FDE型の案件に向くかの判定 |
| 商談の準備 | ヒアリングの質問を商談前に用意する |

### 4.5 情報の区別（2026-09-20追加）

リードの詳細に「このリードの情報の区別」がある。記録している情報がどれにあたるかを必ず選ぶ。

| 区分 | 意味 |
| --- | --- |
| 本人申告 | 相手が直接答えた内容 |
| こちらの解釈 | 推測を含む、こちらの読み |
| 未確認 | まだ確かめていない |

初期値は「未設定」。何も選ばなければ未設定のまま残り、アプリが勝手に確認済みへ変換することはない。サイトの相談フォーム等の選択回答だけで受注可とは判定しない運用を、この欄で支える。

「相談メモの貼り付け」は、相談フォームの内容を手動でコピーして貼る欄。専用の取り込み機能はない。貼った内容は本人申告として上の区別に反映する。

## 5. 案件モード（9つの帳票）

受注したら案件を作る。1案件につき9つのタブが並び、上から順に進める設計。各タブの右上の印が進捗になる。

### 5.1 ① 案件設定

案件の土台。企業情報・面談日・プラン区分を入れる。

主な欄:

| 欄 | 内容 |
| --- | --- |
| 企業情報 | 企業名・担当者・面談日など |
| FDE商品と個別仕様 | FDE商品区分（build等）・価格の状態・契約額・試験範囲・納期の前提 |
| 情報利用条件 | この案件で使ってよい情報の範囲（三層分離の入口。後述） |
| 利用する基準の版 | 知見台帳から採用した知見のIDと版をここに固定する |
| 共通メタ | 版・根拠・確認者・変更理由・適用期間 |

価格の状態は「合意済み」など段階で管理する。契約額は税抜で入れる。

### 5.2 ② ヒアリング設計

商談で聞くことを整える帳票。

FDE受注条件の確認（7項目）:

1. 毎月案件が動き、照合・未処理・例外の判断が繰り返し発生する
2. 顧客の責任者と代行者がおり、原資料と最終業務判断を担える
3. 顧客が事務所の操作を待たずに停止・手動処理・資料取得を行える
4. 代表的な繁忙量でも、手動代替が実際の期限内に終わる
5. データ、設定、手順、試験結果、必要な利用権を顧客側に残せる
6. 内製・他社等との費用・品質・負担の比較ができる
7. 下書き・月次点検で価値があり、即応や無人での重要操作を必要としない

各項目は「合っている／合わない／未確認」の3値。1つでも未確認が残る案件は受注可否を未判定のままにする。

### 5.3 ③ 業務フロー分析

現行の業務の流れと、導入後の流れを対比させる。

- 運用設計（人とAIの分担）: どの判断を人が持ち、どの処理をAIが下書きするかを明記する

### 5.4 ④ 単価設計

料金の根拠を作る帳票。料金プリセットは2026-07-25に確定した料金表（税抜）に基づく。

主な仕組み:

- 継続価値の比較（A/F）: A=顧客が次善の手段（内製・他社）に払う全管理費用、F=こちらの料金。A/Fが1.5以上なら暫定目安を満たす判定が出る
- 段階別の目安: Defend（防御）5〜8万、Extend（拡張）15〜18万、Transform（転換）55〜80万、月額8〜10万（いずれも2026-07-25確定の設計に基づく目安。最新の料金は公式サイト・見積で確認）

### 5.5 ⑤ 商談後メモ

商談の直後に書く。合意したことと未合意のことを分けて記録するのが要点。未合意を残したまま先に進むと事故るので、ここで分離する。

### 5.6 ⑥ 実行管理

受注後の実務の中枢。4つの区画と知見台帳がある。

構築の4段階:
S1 仕様の固定 → S2 試作 → S3 検証 → S4 引渡し。限定構築はこの順で進め、各段階の合意日を残す。

実行状態:
作る仕事を1件ずつ「+ 仕事」で追加し、11の状態で追う。

下書き → 入力不足 → 実行可能 → 実行中 → 確認中 → 承認待ち → 納品待ち → 完了。異常系は 失敗／安全停止、最後に 終了。

各仕事には次の欄がある。

| 欄 | 決まり |
| --- | --- |
| 担当 | 誰が実行するか |
| 入力識別子・設定版 | 何を入力に使い、どの版の設定で動かすか |
| 期待結果 | こうなるはず、を先に書く |
| 実結果 | 実際どうなったか。未確認は空欄のまま |
| 証拠 | 保存先・記録の参照。秘密情報そのものは入れない |
| 確認者 | 実行者とは別の人が確認する。空欄は未確認 |
| 未実施理由 | 試験していない場合に記入。未実施を合格にしない |

承認台帳:
AIが実行し人が承認する重要操作の記録。承認者・対象・有効条件を固定し、承認後に内容が変わったら再承認にする。結果が未入力のものを承認済みと読み替えない。

変更・事故の記録:
影響・原因の仮説・対応を残す。原因の仮説と確定原因は分ける（仮説が自動で確定に昇格することはない）。失敗または安全停止の仕事があると警告が出る。「知見候補にする」ボタンで、この例外を知見台帳の候補として登録できる。

### 5.7 ⑦ 月次報告

「+ 今月分を追加」で当月の報告ができる。

| 区画 | 内容 |
| --- | --- |
| 月次成果物 M1〜M4 | M1 照合記録／M2 試験記録／M3 権限・依存先・変更影響の記録／M4 月次判断・引継ぎ更新 |
| 時間の4区分 | 本人実働・AI処理・待ち・顧客側作業を分けて記録。月100時間の容量判定に数えるのは本人実働だけ |
| 給付と精算の分離 | 何を届けたか（給付）と金額の精算を別々に記録 |
| 未実施・限定実施・未確認の明示 | やらなかったこと・一部だけのこと・確認できなかったことを隠さず書く欄 |
| 今月の振り返り（2026-09-20追加） | 確認に迷った箇所／事前に発見できたか／次回追加する確認／不要だった記録／記録の負担増／再利用可否 の6欄 |

振り返りは仕組みを育てるための欄。すべての例外を知見化する必要はなく、ノルマでもない。迷ったこと・要らなかった記録を月末に一度だけ見直す。

### 5.8 ⑧ 継続サポート

継続契約の管理。

- 次月の選択: 続ける・縮小・終了など次月の方針
- 依存先の変更記録: 外部サービスの仕様変更など、預かり仕組みが依存している先の変化を記録
- 移管・終了票: 終了時に顧客へ何を返すか（データ・設定・手順・試験結果・利用権）の票
- 知見の見直し: 見直し期限が近い（30日以内）または過ぎている承認済み知見の一覧（2026-09-20追加。内容の確認は⑥の知見台帳で行う）

### 5.9 ⑨ 契約・法務

7点の法務書類＋関連文面を、金庫内の雛形から生成する。

生成できるもの:
NDA、見積書、発注請書、業務委託契約書、AI利用・データ取扱特約、個人情報取扱覚書、検収書、業務完了報告書、免責事項。

書類は金庫の雛形と受託者プロフィール（設定で登録）から自動で差し込まれる。生成した内容はコピーして使う。雛形そのものの直しは 設定 → 書類雛形 で行う。

## 6. 知見台帳（2026-09-20追加の新しい仕組み）

案件で得た知見を、案件をまたいで育てる台帳。⑥実行管理の末尾にある。全案件共通の1冊。

### 6.1 考え方: 情報の三層分離

情報は3つの層に分けて扱う。

| 層 | 例 | 決まり |
| --- | --- | --- |
| 案件固有 | 顧客の数値・社内事情・個別の手順 | その案件でのみ使う |
| 内部の再利用知見 | 一般化した質問・判断基準・試験方法 | 審査を通したものだけ再利用 |
| 公開用見本 | 記事・営業資料に出す例 | さらに別の公開審査を通す |

顧客名を消しただけでは安全な知見とみなさない。内部再利用への承認と公開への承認は別々に行う。

### 6.2 知見の一生（状態遷移）

候補 → 確認中（一般化・利用条件） → 試験待ち → レビュー待ち → 内部再利用承認済み

終了状態は3つ: 却下／要再検証／廃止。終了状態にした知見は削除されず、一覧の「終了した知見」を開くと読める。検索・適用の候補からは外れる。削除できるのは「候補」で、かつ案件への適用記録がないものだけ。

### 6.3 1件の知見に記録する項目

知見ID、題名、種別（質問／判断基準／試験／例外対応／引継ぎ／積算の注意）、何の問題を防ぐか、一般化した内容、適用条件、除外条件、根拠区分（仮説／架空データで試験／実案件で確認）、確認済み範囲、未確認範囲、利用権・秘密・再識別リスク審査、版、承認者、承認日時、見直し期限、適用した案件への参照。

一般化した内容には案件名・顧客名を含めない。確認済み範囲と未確認範囲は分けて書く（未確認を確認済みにしないため）。

### 6.4 案件への適用（版を固定する）

内部再利用承認済みの知見は、案件に「適用」を記録できる。

1. ⑥の知見台帳で知見を開く
2. 「この案件への適用を記録」→ 適用理由を書く
3. その時点の版が案件側に固定される

新版を出しても、適用済みの案件の基準は自動では更新されない。変えたい案件では、新版で改めて適用を記録する。採用した知見のIDと版は①案件設定の「利用する基準の版」にも書く。

### 6.5 例外から知見を作る

⑥の変更・事故の記録にある「知見候補にする」を押すと、その例外が種別「例外対応」の候補として台帳に入る。一般化は台帳側で行う。すべての例外を知見化する必要はない。

### 6.6 見直し

承認済みの知見に見直し期限を入れておくと、期限の30日前から⑧継続サポートに一覧が出る。期限超過は赤く表示される。確認と版の更新は⑥の知見台帳で行う。

## 7. 出力（Excel・Word・印刷）と三区分

案件画面上部の Excel／Word／印刷 は、押すとまず宛先の確認画面が出る（2026-09-20追加。全文一括出力は既定ではない）。

| 区分 | 使い道 | 出力 |
| --- | --- | --- |
| 顧客引継ぎ用 | この案件の内容を顧客に渡す | 可（知見台帳の適用参照など内部限定の情報は含まない） |
| 内部再利用用 | 事務所内での再利用 | 可（外部への持ち出し・公開はしない） |
| 公開用見本 | 記事・営業資料など外部公開 | 不可。一括出力は案件固有情報を含むため使えない。公開承認済みの知見だけを⑥の台帳から個別に取り出す |

区分を選んで「この区分で出力する」で実行。出力は操作の記録（監査）に残る。

## 8. 自社モード

事務所全体を見る場所。

| 区画 | 内容 |
| --- | --- |
| 自社の月次記録 | 月ごとの共通時間・AI費用などを記録 |
| 容量判定（計画） | 本人実働の上限（月100時間）に対し、受注の計画が収まるかを判定 |
| 承認の横断一覧 | 全案件の承認待ち・承認済みを横断表示 |
| 変更・事故の横断一覧 | 全案件の事故・変更を横断表示 |
| 実行状態の横断一覧 | 全案件の仕事の状態を横断表示 |

案件側で記録した承認・事故・実行状態は、ここに自動で集まる。月末は自社モードで全体を見てから各案件の月次報告を締める流れ。

## 9. 設定

右上の設定から開く。6つのタブ。

| タブ | 内容 |
| --- | --- |
| 受託者プロフィール | 屋号・氏名・所在地・メール・ポートフォリオURL・インボイス番号・振込先。法務書類に差し込まれる |
| 書類雛形 | 12種類の雛形。「組込雛形で全部上書き」で最新の雛形に更新できる |
| 文面ライブラリ | 紹介依頼などの定型文 |
| 紹介 | 誰が誰を紹介したかの記録 |
| 保全・端末 | 金庫の守られ方の説明、同期の状態、この金庫を開いている端末の管理、操作の記録（監査ログ） |
| 取込・書き出し | 控え（バックアップ）の取得と復元、旧版（v3）からの取込、削除ポリシー、パスフレーズ変更 |

使わなくなった端末は 保全・端末 から失効させる。パスフレーズを変えると全レコードが新しい鍵で封し直される。

## 10. 典型的な1ヶ月の流れ

1. 問い合わせが来たら リード① で登録。④で情報の区別と7項目を埋める
2. 商談前に リード④ の商談の準備。商談後は合意・未合意を分けて記録
3. 受注したら 案件 を作り、①で企業情報・FDE商品区分・情報利用条件を入れる
4. ②で受注条件7項目、③で人とAIの分担、④でA/F比較と料金の根拠
5. ⑥で仕事を登録して11状態で追う。重要操作は承認台帳、事故は変更・事故の記録へ
6. 再利用できそうな例外は「知見候補にする」。知見は確認中→試験待ち→レビュー待ちを経て承認
7. 月末に ⑦月次報告（M1〜M4・時間4区分・振り返り）を書く
8. 自社モード で容量と横断一覧を確認し、翌月の計画を決める
9. ⑧で次月の選択（継続・縮小・終了）。終了なら移管・終了票で返すものを整理
10. 定期的に 設定 → 控えを取る でバックアップ

## 11. 困ったとき

| 症状 | 確認すること |
| --- | --- |
| 書類が生成されない・固まる | 2026-09-15に金庫同期の競合を修正済み。再発したら操作の記録と cockpit.lastError（設定の保全・端末）を確認 |
| 同期が進まない | 設定 → 保全・端末 → 同期の状態。「同期上限超過」が出ていたら該当レコードが1MB超 |
| 知見が消えた | 2026-09-20に保存漏れを修正済み。それ以降に登録した知見は保持される |
| パスフレーズを忘れた | 復元手段はない。控えのJSONも同じ鍵で閉じている。パスフレーズの控えを探す |
| 表示がおかしい | まずリロード。直らなければブラウザのコンソールエラーを控えて報告 |
| 本番に新機能がない | デプロイ前は本番は旧版のまま。デプロイ後に金庫を開けば新項目は空欄で自動追加される（移行作業は不要） |

## 12. 運用上の決まり（まとめ）

- 空欄は未確認のまま残す。アプリも自分も、空欄を「問題なし」「承認済み」「ゼロ」に読み替えない
- 未実施は未実施と記録する。試験項目が文書にあることと、実装が合格したことは別
- 承認後に内容が変わったら再承認
- 事故の原因は仮説と確定を分ける
- 顧客名を消しただけの情報は再利用・公開しない
- 知見化にノルマは設けない。月末の振り返りで一度だけ見直す
- 控えは定期的に取る
