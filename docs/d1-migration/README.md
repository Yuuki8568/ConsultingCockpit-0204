## 次工程を阻む情報

現行DBの管理画面または、整合したSQLiteエクスポートを取得できる接続経路が必要。通常のCockpit JSONバックアップだけでは認証テーブル・同期番号・監査履歴までの完全なDB移行を証明できない。
秘密のトークンやパスフレーズをチャットに貼らせない。DB管理画面の接続を利用するか、非公開の安全な経路で整合したエクスポートを扱う。DBダンプをGitHubにコミットしない。

## 実装・切替の順序

1. 旧DBのサービス・スキーマ・規模を確認し、整合したスナップショットを取得。認証情報を含むためアクセス制限する。端末側未同期データ・録音原本も別途保全。
2. 実データとは別の検証用D1を用意し、DrizzleのD1アダプターとBetter Authの互換性を検証。現行DBは引き続き使用する。
3. `sync.ts` の読込後条件分岐を伴うトランザクション、`vault.ts` の金庫作成・鍵変更をD1向けに設計し直す。単純なtransaction削除や非原子的な逐次実行は禁止。競合、世代番号、端末失効をSQL条件と原子的な更新で保持する。
4. user/vault/recordのID、暗号文、IV、KDF、世代番号、監査連鎖を変更せず移す。同一サービスの保存先変更であるため、以前のRunable移行用スクリプトのID変換・端末失効方針を無条件に流用しない。OAuth資格情報・セッションの移行/再ログイン方針を別途決める。
5. D1の行サイズ・SQLパラメーター数・バッチ制限を確認し、上限付近の暗号化レコードを試す。
6. 全テーブルの件数と暗号化業務レコードの内容を照合し、本人による復号、顧客/案件/営業/書類/文字起こし表示を確認。D1の復元機能と独立バックアップからの復元を検証する。
7. 全端末の同期を確認して短時間の更新停止を実施。最終差分をコピーし再照合した後だけ、対象WorkerのバインドとDB実装を切り替える。
8. 保存・再読込・別端末同期・競合・鍵変更・権限拒否を確認。旧DBは保持する。切替後の更新を保全せず旧DBへ戻さない。

## 合格条件

- 暗号文/IV/KDF/監査履歴の照合一致、無関係ユーザーのアクセス拒否。
- 同時更新で取りこぼしや世代違いの混入がない。
- 現行の契約雛形、締結済み本文、案件別事実が勝手に書き換わらない。
- D1への保存完了を確認してから「同期済み」と表示。
- ブラウザー消去を前提にした復元テスト、原本は別系統で復元。
- 残存バックアップの期限・旧DBの削除予定を記録し、完全削除済みと誤表示しない。

## 将来の共同管理

単なるOWNER_EMAILS追加では各利用者が別の金庫になる。事務所共通領域、招待、個人アカウント、閲覧/編集権限、監査、失効を実装する。端末側暗号化を維持するなら利用者ごとの鍵の配布・更新・回収限界を設計する。現段階で利用者は追加しない。
