# 長期運用と費用抑制（2026-11-06）

## 方針

所有者1名、将来少数の信頼できる共同利用者、MacとAndroidでの利用を前提とする。顧客・案件本文は引き続き端末内で暗号化する。DB選定だけで大容量対応が完了したとは扱わない。

候補は Workers Paid + D1。既存のCloudflare配信・Access・監査保存先を活かし、常時稼働DBの時間課金を避ける。実際のlibSQL接続先の所有権・料金・運用条件が良好なら、現DBの継続にも移行事故を避ける価値がある。料金プラン変更と本番コピーは今回行っていない。

録音・動画はDBへ詰め込まない。将来のクラウド保管には端末側で暗号化してからR2へ保存する方式を候補とする。現在の原本保存・バックアップの方式を変更したり、原本を自動アップロードしたりはしていない。R2の導入前に、復号鍵・分割アップロード・再開・容量制限・保存世代・削除権限を設計する。

## 今回のコード変更

| 対象 | 改善 | 残る制約 |
| --- | --- | --- |
| D1同期 | 全暗号文の取得を、変更対象最大8件と差分ページへ縮小 | 全体件数・容量のSQL集計は残る。DB読取行数が一定になるわけではない |
| libSQL同期 | 最大256件・推定4MiBの基本ページ、メタデータの先読み257件 | 競合データは別途最大8件追加。全応答4MiB保証ではない |
| 端末内の未送信取得 | dirty索引とcountを使用。送信8件/3MiB、走査128件ずつ | 全件再構成・復号、通常編集の全体CAS/HMAC検証は残る |
| 端末内の通常保存 | 全件消去・再挿入から変更行のみの保存へ | 同時編集・鍵変更・復元との衝突検査は全体で維持 |
| 定期監査証跡 | 既存の末尾はハッシュだけ取得し、差分照会とまとめる | 5分間隔、連鎖検査、別保存先への記録を維持。全履歴を毎回検査する処理ではない |
| 容量確認 | 設定のボタンで使用中・削除済み・履歴・監査の内訳を取得 | 論理容量であり、DB物理容量・索引・全テーブル・請求額ではない |

容量集計は利用者ごとに毎分3回まで。画面表示・フォーカス・通常同期のたびには集計しない。顧客名・本文・暗号文・レコードIDは集計応答に含めない。70%/90%で注意表示するが、課金の強制停止や自動通知は実装していない。

署名付き更新、一回限りの追加認証、端末失効、世代保全、原子的監査記録、独立証跡との照合は維持する。過去世代を費用削減のために自動削除しない。

## 大量投入前に解消する制約

1. **鍵変更の分割処理**。現D1は使用中1,000レコード、送信4MiB等の上限があり、暗号文だけで4MiB未満でもJSON・鍵情報の分だけ早く上限に達する。新世代の暗号文を別領域へ少量ずつ準備し、旧版との一致・署名・件数・ハッシュを確認してから鍵世代を原子的に切り替える設計が必要。途中失敗で旧データを読めなくしない。単に1,000件制限を外さない。
2. **全監査検証の分割**。現D1の手動全検証は10,000件/16MiBまで。固定した末尾と独立証跡に結び付いたページ検証へ改める。部分検証を全件合格と表示しない。
3. **大きい案件の分割**。1件のbase64暗号文上限は1MiB（平文は概ね768KiBより小さい）。書類・文字起こし・大きい共通設定を独立した暗号化レコードへ分け、案件から参照する。検索のために顧客本文を平文の索引へ出さない。
4. **長期履歴の保存設計**。毎回の編集で旧暗号文の世代を保存するため、顧客数より編集回数が容量を増やす。大容量時は署名済み目録・ハッシュ検証付きの暗号化アーカイブを検討する。通常の同期権限から過去世代を消せない原則を保つ。
5. **端末の段階読み込み**。現在は金庫全体をメモリへ再構成する。特にAndroidでは端末のメモリを測定し、一覧の段階表示・必要な案件だけの復号へ改める。合成試験だけで実機の数万件運用を保証しない。
6. **移行の分割**。準備済みの初期移行は全体2,000行/16MiB等で停止する。上限超過時は継続チェックポイントと分割照合を設計する。DBの上限とこの移行ツールの上限は別である。

今回のD1同期も総1,000行/16MiBの安全枠を残す。容量判定は暗号文・IVに1行1KiBの余白を加えるため、旧判定の限界付近では早めに拒否することがある。旧形式の同一seqグループが256件またはページ容量を超える場合は、取りこぼさず明示的に停止する。実データのseqを勝手に変更しない。こうした制限は容量画面と移行事前確認で把握する。

## 費用の考え方

2026-11-06確認の公式料金。米ドル、税・為替・他サービス利用料は別。アカウント全体の他Worker/DB利用分も含むため、Cockpit専用の上限額ではない。

| 項目 | 含まれる枠 | 超過分 |
| --- | --- | --- |
| Workers Paid | 最低月額$5、1,000万リクエスト、CPU3,000万ms/月 | $0.30/100万リクエスト、$0.02/100万CPUms |
| D1 Paid | 月250億行読取、5,000万行書込、計5GB | $0.001/100万読取、$1/100万書込、$0.75/GB月 |
| R2 Standard（将来候補） | 月10GB、Class A100万回、B1,000万回 | 容量$0.015/GB月、操作料別 |

たとえば月100万Worker実行・平均CPU30ms・D1の各利用量が付帯枠内なら、この範囲の計算は月$5。ただし実測や将来の請求保証ではない。監査、認証、静的配信前のWorker実行なども含めて測る。録音・動画の保管や文字起こしAPI利用料は別枠で管理する。

費用判断はCloudflareの実際のCPU・リクエスト・D1読書行数・物理保存量の集計を使う。今回の容量画面から請求額を逆算しない。Paidでは付帯枠超過分に課金されるため、「月$5で無制限」や「一定額で自動停止」と説明しない。

## 検証と反映

合成データでページ境界、旧seq同値、容量超過、他利用者分離、署名改変・再送、競合、失効、取引取消、IndexedDB中断、モバイル幅を検証する。所有者による既存の復元確認・Mac/Android実機確認は完了済みとして扱い、再実施を要求しない。

この変更はレビュー用ブランチの候補。新しい課金契約、D1への本番移行、顧客契約の変更は実施していない。大規模利用を完成済みと表現しない。料金・移行方式の決定後にも、実件数・容量が検証済みの範囲内であることを確認してから本番切替を行う。
