# 分割移行の実行制御と棚卸し

この手順は、通常のCockpitから切り離した移行先で、承認済みの作業を1回ずつ進めるためのものです。実データのD1移行は保留中です。通常のWeb画面や定期処理から起動する経路はありません。

## 棚卸しの判定

`inspectSourceInventory` は移行元の読み取り専用トランザクションで、主データベースの表・索引・ビュー・トリガーを調べます。業務18表と索引の計49定義を設計と照合し、許可したSQLite管理表があれば別に数えます。業務行は取得しません。未知のオブジェクトや定義の違いがあれば、内容を外に出さずに停止します。

`inspectMigrationInventory` は移行先も照合します。既知の提供者管理表の名前と定義を確認し、その中身を読みません。業務表と移行用の管理表には、空であることを要求します。コピー進捗、独立照合、実行制御、原子的更新の補助表がそろっていることも条件です。棚卸し処理は表の作成・変更・消去を行いません。

## 実行と再開

1. 移行元・移行先の接続先を特定し、書き込み停止と移行先の隔離を別途確認します。契約条件・実行許可がそろった段階で、棚卸しと利用量の実測結果から実行期限と上限を決めます。
2. `initializeExecutionControl` が棚卸しを実施し、1つの実行IDに期限、累計試行回数、UTC日ごとの読み取り・書き込み・リクエスト上限を固定します。同じ台帳の再初期化で回数や期限を戻すことはできません。
3. `runControlledMigrationStep` がコピー開始、コピー1段階、独立照合開始、照合1段階、完了記録の確定のいずれかを引き受けます。利用量は信頼できる計測元から渡す必要があります。データベースの時刻を使い、当日分で60秒以内の取得値だけを受理します。別の処理が実行中、残量不足、期限切れのいずれかなら開始しません。
4. 各回の開始時に試行回数と使用見込みをまとめて記録します。業務行・進捗の確定時にも、同じ実行権が有効かを同一トランザクションで再確認します。実行権は最大30秒で、全体の期限またはUTCの日替わりにも失効します。
5. 通信失敗や応答喪失の際は、同じ実行IDの台帳とコピー・照合の保存済み進捗を読みます。確定済みの処理を二重に送らず、未確定なら失効と残量を確認してから次の1回を判断します。試行済みの枠は戻しません。

実行制御の表を作成した移行先では、旧方式の一括コピーも停止します。一括コピーの開始後に制御表が作成された場合は、以後の業務データ書き込みと完了記録の更新を拒否します。

## 使用量の読み方

1回の予約はD1の読み取り16,384行、書き込み128行、Workerリクエスト4回、保存容量131,072バイトです。これらは保守的な見積もりです。日次枠はUTC日替わりで更新し、累計試行回数と保存容量の見込みは実行期間を通じて保持します。全体期限の上限は7日、累計試行回数の上限は12,000回です。実行ごとにより小さい値を設定できます。

検査、台帳作成、拒否応答、状態確認、計測値の取得、同じアカウントの他の利用は、各段階の予約とは別に利用枠を消費します。利用統計の反映遅れや処理中の他サービスの消費があり得るため、請求額や実CPU時間の上限をこの台帳だけで保証することはできません。実行前には実際のFree利用状況と代表的な処理のCPU・行数を測定してください。[D1の利用量と料金](https://developers.cloudflare.com/d1/platform/pricing/)・[Workersの利用制限](https://developers.cloudflare.com/workers/platform/limits/)

実データで残る確認は、移行元の実棚卸し、全書込元の停止と処理の終了、無料枠での実測、切替記録の受入れ、直前のバックアップと端末確認です。有料化が必要な場合は、金額と理由を示してから変更を判断します。
