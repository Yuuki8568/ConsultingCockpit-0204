# D1を無料枠で移行する計画と事前検査（2026-11-10）

## 結論と今回の完了範囲

D1はWorkers Freeで利用できる。現在の一括移行Workerをそのまま配備できない理由は、CPU上限30000msを要求し、全表のコピーと監査照合を1回で処理するためである。有料化だけが選択肢ではない。

無料枠を維持する第一案は、処理を小分けにし、進捗をD1内へ記録する移行方式である。今ある一括処理からCPU設定を消すだけでは採用しない。Workerの処理量を減らすために、照合・失効情報・監査記録を省略しない。

今回完了したのは、制約の確認、以下の設計、および**本文を出力しない読取専用の事前検査**と架空データ試験である。分割コピーエンジン、実データへの事前検査、実CPU計測、本番移行は未実施。現用のlibSQL経路と既存の切替検証条件は維持する。

## 無料枠の基準

2026-11-10に公式資料で確認した基準。実行直前にも再確認する。

| 項目 | Workers Free / D1 Free |
| --- | --- |
| Worker CPU | HTTP・cronとも1回10ms。通信待ちはCPU時間に含まれない |
| Worker要求数 | アカウント全体で1日100,000回 |
| D1の読み取り | アカウント全体で1日5,000,000行 |
| D1の書き込み | アカウント全体で1日100,000行。索引・進捗記録も消費する |
| D1容量 | 1DB 500MB、アカウント合計5GB |
| 1行 / SQL / bind | 2,000,000 bytes / 100,000 bytes / 100パラメーター |
| D1呼出回数 | 1回のWorker実行で50回。batchは全体で1回として数えるが、各SQLの制限は残る |
| 無料枠超過時 | 日次行数の上限で照会が失敗し、翌日00:00 UTC（日本時間09:00）まで待つ。自動的に有料化する設計にしない |

根拠：[Workersの制限](https://developers.cloudflare.com/workers/platform/limits/)、[D1の制限](https://developers.cloudflare.com/d1/platform/limits/)、[D1の料金](https://developers.cloudflare.com/d1/platform/pricing/)。D1のTime TravelはFreeで7日だが、端末内だけにある録音・動画原本のバックアップではない。

## 追加した事前検査

`security-ops/d1-free-preflight.ts` の `inspectFreeMigrationTable` は、指定されたスキーマ内の1表を1回ずつ調べる。外部入力のテーブル名・列名をSQLとして使わない。

- libSQLは読取トランザクション。件数、値のバイト数合計、最大行、未対応型の有無をSQLで集計する。
- ソースと移行先の列名・主キー順、移行先件数・索引数を確認する。利用者表は許可された確認済み所有者のみかを集計で調べる。
- 行本文・メール・利用者ID・認証情報を戻り値に入れない。SQL実行失敗は固定のエラーコードに置換する。
- 移行先は読取のみ。コピー、消去、初期化、既存の切替用receipt生成は行わない。公開API・cron・本番入口から呼ばない。
- 18表全体は同一時点のスナップショットではない。列と主キーの一致は、索引定義・制約・外部キー・監査・値の一致を証明しない。

`planFreeD1Migration` は18表が揃っているかを検査し、下記の仮定で必要な処理量の予備枠を見積もる。`fitsPlanningReserve` は容量見積もりの条件にすぎず、`cutoverAllowed` と `migrationImplemented` は常にfalse。アカウント使用量が不明なら不明として返す。

見積もり仮定：主キー索引を使う1行単位の4パス、監査2パス、表ごとの準備と終了処理、各実行に進捗・試行記録の索引を含め8行の書込予備枠を置く。これは実測値、厳密な上限、請求額ではない。全表走査を繰り返す実装は仮定を満たさないため、実行時の `rows_read` / `rows_written` とアカウント全体の残量を別に計測する。

JSONの1行上限は、文字のエスケープを考慮した保守的な計算値。64KiB超なら、実際の行サイズ計測または列内分割の設計が必要と判定する。64KiBは開発上の初期目標であり、「このサイズなら10ms以内」と保証しない。現行アプリの業務レコード1,000行・セッション100行の上限も維持する。同期総量や復号時メモリなど他のアプリ制限を緩めるものではない。

## 分割移行の実装設計（まだ実装していない）

2026-11-13追記：このうち「少量の読取」は独立した非公開運用部品として実装・架空データ試験を追加した。詳細は[読取工程の記録](d1-bounded-reader-20261113.md)を参照。分割コピー全体・本番への接続・切替は引き続き未実装／未実施。

1. **事前判定**：実件数・最大行・完全なスキーマ・空の管理表・既存の失敗記録・独立監査証跡を確認。現用DBの契約・保存地域、移行先との契約上の整合も確認する。容量不明や超過は停止し、プランを自動変更しない。
2. **書込みの停止**：通常の `COCKPIT_READ_ONLY` だけでは認証や回数制限の書込みが残る。既存の全HTTP拒否の保守入口を使う前提とし、認証・API・監査cronを含めて停止する。旧版の実行が残っていないことと待機期間を確認する。公開された移行APIや新しい認証トークンを追加しない。
3. **1回の仕事を固定**：主キーを使ったkeyset方式で1行または小さい固定ページを読む。OFFSETで同じ先頭を繰り返し走査しない。大きな行はSQLで大きさを確認してから取得し、取得クエリにも同じ上限条件を入れる。上限を超える1行は失敗として隔離し、無制限に読み込まない。
4. **進捗とコピーの同時確定**：run ID、スキーマ版、相、表、主キーカーソル、件数、累積ハッシュ、試行回数をD1に保持する。対象行のINSERTと進捗の更新は、期待する旧進捗を条件に同じ原子バッチで行う。UPDATE/REPLACEで既存の業務行を上書きしない。通信切断後は確定済み進捗を読み、同じ行を重複挿入しない。並行実行・古い進捗は拒否する。
5. **中断と失敗を分ける**：CPU打切りや通信の結果不明はリース期限後に進捗を読み直す。制約違反、所有者違い、ハッシュ不一致は隔離して自動再試行しない。連続失敗は回数上限で停止する。無料枠の日次残量不足は翌日以降の再開候補とし、保持中の書込み停止時間を事前に見積もる。
6. **別パスで照合**：コピー時、移行先の独立読戻し、元DBの再読込で、同じ順序・正規化・スキーマ版を使うハッシュを比較する。監査連鎖も1イベントずつ照合し、前後で独立証跡に照らす。件数だけの一致で完了にしない。
7. **形式を混同しない**：現行の一括移行ハッシュは配列全体のJSONを対象にする。分割用の累積ハッシュは別形式のため、v2の形式識別子と検証器を明示的に実装・試験する。v1の完了記録を偽装して使わない。
8. **切替判定**：すべての相を通過し、対象のハッシュを固定してから読取制限付きでD1を接続する。本人による解錠・既存データの確認と、通常の認証・同期の確認後に書込みを開く。D1へ書き始めた後に、コードだけをlibSQLへ戻してはならない。

新しい定期実行やバックグラウンドジョブは追加していない。実行経路・停止時間・再開手順を具体化するまで、既存の本番cronも変更しない。

## 検証と限界

架空のローカルlibSQLとローカルD1で18表を検査。読取SQLしか実行しないこと、本文を返さないこと、所有者・スキーマ・未対応値・不正な表名の拒否、UTF-8とJSONの上限、日次使用量・容量・大きな行・現行アプリ上限の判定を確認した。実行開始時の例外にも秘密を含むエラーを出さない。既存の一括移行試験も継続し、共有スキーマ定義の抽出による動作変更がないことを確認する。

このローカル試験はFreeプランのCPU10ms以内を証明しない。事前集計もDB側では全表を走査し得るため、実環境のSQL所要時間・現用DB側の利用条件を確認する。実データの事前検査は今回まだ行っていない。追加した事前検査の結果は非公開の運用情報として扱い、実件数や顧客情報を公開PRへ転載しない。
