# D1分割移行：業務表の構造と外部キーの検査（2026-11-17）

## 実装した範囲

既存の18業務表について、移行前検査・1行ずつの読み取り・コピー先検査・独立読戻しに、表と全索引の定義照合を加えた。列名と主キー名だけが同じでも、型、必須指定、初期値、主キー順序、UNIQUE、照合順序、部分索引、外部キー、関連するトリガー・ビューが異なる場合は停止する。公開運用のHTTP・cron入口には接続しない。

承認済みの `cloudflare/d1/business-schema.sql` を架空の空SQLiteへ適用して得た `sqlite_schema` のSQLバイト列をSHA-256で固定したものが `security-ops/d1-schema-contract.ts`。外部DBから学習・自動更新しない。ローカルlibSQLとMiniflare D1で同じ定義を確認し、Node cryptoによる独立計算とも比較する。元のSQLファイルだけを変更した場合も既存の移行試験で不一致になる。

SQLの小文字化・空白除去で文字列リテラルの違いを消さない。書式だけが異なる同等の定義も意図的に拒否するため、実DBの定義と合わなければ内容を個別に確認する。互換性のためにその場で基準を書き換えたり、実DBの構造を修復したりしない。

## 読み取りと停止条件

定義の読取は1表ずつ。SQLは1オブジェクト16KiB、名前は128バイト、件数は期待件数+1に制限してからDB境界を越える。SQLはhexで取得し、NULなどの切詰めによる比較誤りを避ける。SQL本文・利用者ID・違反した行は戻り値やエラーへ出さない。定義の不一致と問い合わせ失敗は、どちらも成功へ読み替えない。

外部キーの違反は、事前検査および各表の読取終了時に検査する。DBから返すのは違反の有無のみ。行ごとの再走査は行わない。主データベースを明示した読み取りにして、一時表などによる参照先の取り違えを避ける。D1では主系から始める同一セッションを使うが、全表の固定スナップショットではない。

コピーの初期化と各ステップで移行先の定義が違えば、業務行と進捗を書き込む前に停止する。独立照合中の定義不一致・外部キー不整合は実行を `failed` にし、再開しない。実行時のスキーマ識別値にも固定した定義を含めたため、今回より前の弱い識別値で作った進捗は再利用できない。自動変換・削除は実装しない。

## 確認範囲

- 18表の正しい定義をローカルlibSQL/D1で照合。
- 必須指定、型、初期値の大文字・空白、複合主キー順序、外部キーの欠落・削除動作、重複禁止、照合順序、部分・降順索引、追加索引・トリガー・ビュー、過大なSQL・名前・件数の17条件を拒否。
- 架空の参照先欠落を実SQLiteで作り、事前検査・読取終了時・独立照合で拒否。独立照合の失敗は再開不可。
- コピー開始前・途中の構造差異で業務行と進捗が増えないこと、旧スキーマ識別値の拒否、問い合わせエラーの内容を公開しないことを確認。
- 既存の複合キー読取、原子的コピー、再開、監査連鎖・独立証跡の試験も維持。

検査は変更ファイルに限定したGitleaksと手動レビュー。Semgrepは承認済みローカルルールがなく未実施。依存変更がないためOSVは対象外。スキル変更がないためCiscoの開発検査は対象外。追加の任意レビュー手順の取込みは既存検査基準との差異により保留し、設定や基準を変更しない。リモート連携の内部実装は未検証。実サイトのZAP検査は実施しない。

## 未完了と本番の扱い

この工程は業務表に限定したコードと架空データの検証であり、実DBの全体検査ではない。移行対象外の表・提供者管理表の棚卸し、全管理表の最終定義・空状態、全書込元の停止、実接続の識別確認、実行期限・リース・試行上限・日次残量、最終receiptと受入れ処理、実データによる事前検査・無料枠CPU測定が引き続き必要。SQLの出力上限はDB内部の処理量や課金の上限を保証しない。

ユーザー指示に従い、実データのD1移行は保留。本番は従来のlibSQLを継続し、D1へ新管理表やデータを作成しない。契約・保存地域は未確認。有料プラン・新しいサービス・認証情報・定期処理・CIジョブを追加しない。確認済みのコードを既存の本番ブランチへ反映することと、業務データの保存先切替を区別する。
