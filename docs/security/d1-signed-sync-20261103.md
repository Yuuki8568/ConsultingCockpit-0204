# D1本移行：署名付き同期・鍵変更の実装（2026-11-03）

この変更は移行候補であり、本番Workerの保存先・バインディング・実データは変更しない。

## 実装

- 現行のDrizzle定義から認証、金庫、レコード、履歴、署名鍵、端末、監査、制限カウンターを含むD1用初期スキーマを生成。既存DBには適用しない。空の検証用ターゲット専用。
- 同期と鍵変更の入力検証定義を共通化。既存libSQL経路の入力仕様は維持。
- D1同期処理は、一貫した読取バッチから計画を作り、署名・チャレンジを確認した後、一回の書込バッチで確定する。
- 確定時にセッション期限、端末失効・セッション結合、鍵世代、署名鍵版、レコード件数と最大seqを再確認。初回検証直後の失効・同時更新も拒否する。
- チャレンジ消費、上書き前の暗号文と旧KDFの保全、レコード更新、監査と末尾更新を一括処理。書込失敗時に全体を取り消す。署名なしの代替経路はない。
- 送信量・件数・頻度の制限カウンターは業務更新とは別に確定し、拒否時もカウントを保持する。
- D1鍵変更では操作対象に結び付いた一回限りの本人確認を消費し、全対象のbaseSeq・件数を確認。暗号文、署名秘密鍵の暗号化包み、KDF、世代、監査を一括変更する。
- 応答紛失後の鍵変更再試行は新しい本人確認が必要。同じ本人確認の再使用は拒否する。

## 検証済み（架空データ・ローカルD1）

- 新規保存、暗号文そのままの読み戻し、署名なし拒否、署名後の改変拒否、再送拒否。
- 同時更新は片方だけ採用。古い版は競合として返す。敗者による履歴・監査の残存なし。
- 監査保存の後半で故意に制約違反を起こしても、暗号文・履歴・チャレンジ消費が全て元に戻る。
- 別利用者、失効端末、検証後から確定直前までの端末失効、古い鍵世代を拒否。
- 鍵変更の本人確認なし・古いbaseSeq・本人確認再使用を拒否。
- 鍵変更時の監査失敗で暗号文・署名鍵世代・金庫世代・本人確認消費が元に戻る。
- 鍵変更の読取後に別の更新が入ると拒否。正常変更と新しい本人確認による同内容再試行は成功。

## 現段階の制限

- D1実装は本番ルーターから呼ばれない。OAuth/Better Auth・パスキー登録/確認・端末登録/失効・金庫新規作成/全消去・監査照合・制限付き解錠のD1経路は未統合。
- 同期の検証用スナップショットは1000レコード、暗号文総量16MiBまで。SQL側のサイズ条件で大きな結果を先に抑制し、不一致時は拒否する。HTTP相当の入力上限は4MiB。大きい金庫はページング設計の拡張が必要であり、制限を無視して切り替えない。
- 本番へ移行する前に、全テーブルの整合したコピーと読み戻し照合、認証・端末制御・正常同期の結合試験が必要。
- 所有者確認済みの実データ復元試験は再実施していない。実データの取得・コピー・変更もしていない。
- 契約文面はD1移行済みとして確定しない。Android実機確認も別途未完了。

## 実行

- `bun run typecheck:security`
- `bunx tsc --noEmit -p packages/web/tsconfig.d1.json`
- `node tests/d1-atomic-batch.cjs`
- `node tests/d1-signed-sync.cjs`

初期SQLの再生成は `cd packages/web && bun tests/generate-d1-schema.ts`。ローカルの空のメモリーDBからSQLを生成するだけで、本番への接続や適用を行わない。
