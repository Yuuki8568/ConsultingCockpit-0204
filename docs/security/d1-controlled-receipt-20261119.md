# 分割移行の再開と完了記録

## 実行できる範囲

本番の通常の画面と定期処理には、移行を開始する入口はありません。実データのD1移行は保留中です。以下は、許可済みの作業で移行先を隔離し、外部の書き込みを止めた後に使う内部処理の説明です。

1. 移行元の接続先、契約上の保存地域、直前バックアップ、移行先の接続先を運用記録と照合します。全書込元と処理中の作業を調べます。通常の閲覧モードでも認証・端末登録は書き込みを伴い、既存の定期処理は監査証跡を更新します。すべての書き込みの停止と終了を確認してから作業を始めます。
2. 全オブジェクトの棚卸し、使用量、時間と回数の上限を確認し、隔離した移行先の台帳を一度だけ初期化します。完了記録用の表もあらかじめ用意します。既存の完了記録や以前の移行行がある移行先の再利用は避けます。
3. `advanceControlledMigration` を明示的に1回呼び出すと、保存済み進捗に基づき最大1段階を実行します。各段階は台帳から利用枠を予約し、有効な実行権を確認して書き込みます。失敗が保存された実行は停止します。応答が途切れたら同じ実行IDと範囲で状態を確認し、処理中の実行権が失効してから再開します。
4. コピー、移行先の読戻し、移行元の再照合、監査証跡の最終照合が成功した場合に完了記録を1回だけ保存します。記録には実行ID、設計・対象範囲・コピー・監査を識別するハッシュ、件数、バイト数、照合した進捗番号などを含みます。運用者は記録全体のSHA-256を非公開で保管します。確定直後に通信が途切れても、同じ記録を読み戻せます。

## 保存先を選ぶ際の照合

本番がlibSQLを選択している間、Web画面と定期処理はD1の完了記録を読みません。将来D1への切替が別途承認された場合、分割方式には `v2:` を付けた完了記録のSHA-256を指定します。アプリはD1の主系から記録を照会し、形式、進捗の整合性、件数の上限、記録全体のハッシュを照合します。記録が複数ある場合、形式が異なる場合、指定したハッシュと一致しない場合は開始を拒否します。分割方式の完了記録と対応するコピー・照合・実行台帳は、切替後も保持します。切替時には同じ移行先に記録がそろっていることも確認します。従来の一括方式の照合は従来の形式で行います。

この記録が証明するのは、指定した実行でコピーと照合が完了したことです。書き込み停止の継続、実接続の識別、契約、実CPU・使用量、本人による端末確認は運用時の確認事項です。利用量の集計には遅れや推計が含まれます。日別の集計値を、各操作の直前に必要な信頼できる計測値として流用しないでください。切替後にD1へ書き込みが始まった場合は、両方のデータを照合するまで保存先を戻さないでください。
